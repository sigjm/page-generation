이 프로젝트에서 멀티 에이전트 오케스트레이션을 **실제로 어떻게 썼는지** 적은 기록이다.
지켜야 할 규칙은 [`orchestration.md`](orchestration.md)(운영 규약)에 있고, 이 문서는 그 규약으로
무엇을 얼마나 어떤 방식으로 맡겼는지, 쓰면서 무엇을 고쳤는지를 다룬다.

- 대상 기간: 2026-09-09 ~ 2026-10-05
- 집계일: 2026-10-06
- 근거 자료: 저장소 루트의 `.orchestration/` (브리프·보드·보고서). 런타임 상태라 git 에는 올리지
  않으므로, 이 문서의 수치는 집계일에 그 폴더를 세어 얻은 값이다.

## 2. 구성

### 역할

| 역할 | 누가 | 하는 일 |
| --- | --- | --- |
| 사용자 | 팀 담당자 | 방향 결정, 이미지 품질 육안 확인, 머지·외부 전달 승인 |
| 지휘자 | Claude Code | 작업을 쪼개 브리프로 쓰고, 결과를 코드·테스트로 검증해 수용·반려를 정한다 |
| 워커 | Codex, Antigravity | 브리프 한 건을 수행하고 같은 파일 하단에 결과를 적는다 |

### 폴더

```
.orchestration/                 git 에 올리지 않는다
├── board.md                    배정 보드 (시각·워커·작업·브리프 경로)
├── tasks/                      브리프. 워커가 같은 파일 하단에 "## 결과"를 적는다
├── briefs/                     여러 워커에 나눠 준 라운드의 워커별 지시서 (검수·수정·이름 변경 등)
├── proposals/                  교차검증에서 워커가 각자 낸 제안서
├── reports/                    검수 보고서, 실증 테스트 증거 (화면·로그·JSON)
├── scratch/                    측정 스크립트와 결과 파일
└── watch/                      반복 감시 루프의 사이클별 상태
scripts/orchestration/
├── orc                         지휘 도구 (list / send / task / wait / read / board)
└── workers.tsv                 워커 등록표 (별칭·tty·종류·작업 중 판별 패턴·티어)
```

## 3. 한 건이 흘러가는 순서

```
설계 → 브리프 작성 → 한 줄 전달 → 워커 수행 → "## 결과" 보고 → 지휘자 검수 → 수용 / 후속 브리프 / 반려 → 커밋
```

| 단계 | 주체 | 내용 |
| --- | --- | --- |
| 1. 설계 | 지휘자 | 무엇을 고칠지와 합격 기준을 정한다. 워커에게 설계를 묻지 않는다 |
| 2. 브리프 | 지휘자 | `orc task <별칭> "제목"` 으로 `.orchestration/tasks/<시각>-<별칭>.md` 를 만든다 |
| 3. 전달 | 지휘자 | 워커 터미널에는 "그 파일을 읽고 수행하라"는 한 줄만 들어간다 |
| 4. 수행 | 워커 | 브리프의 담당 경로 안에서만 작업한다 |
| 5. 보고 | 워커 | 변경 파일, 검증 방법, 미해결 이슈를 브리프 하단에 적는다 |
| 6. 검수 | 지휘자 | `orc wait` 로 끝을 확인한 뒤 `git diff` 와 테스트로 직접 검증한다 |
| 7. 판정 | 지휘자 | 수용하거나, 지적을 담은 후속 브리프를 낸다 |
| 8. 커밋 | 지휘자 | 논리 단위로 커밋하고 PR 을 올린다 |

긴 지시를 터미널에 직접 넣지 않는 이유는, CLI 프롬프트가 개행에서 바로 제출되어 지시가 중간에서
끊기기 때문이다.

## 4. 브리프에 쓰는 것

| 항목 | 쓰는 내용 | 넣게 된 이유 |
| --- | --- | --- |
| 작업 성격 | 수정인지, 읽기 전용 검수인지, 교차검증인지 | 검수를 맡겼는데 파일을 고치는 일을 막는다 |
| 증상 | 실측 결과와 그 산출물 경로 | 워커가 같은 현상을 다시 재현하느라 시간을 쓰지 않는다 |
| 이미 배제한 원인 | 확인이 끝난 가설 | 같은 곳을 다시 파지 않는다 |
| 담당 경로 | 고쳐도 되는 파일, 건드리면 안 되는 파일, 다른 워커가 작업 중인 파일 | 두 워커가 같은 파일을 동시에 고치지 않는다 |
| 합격 기준 | 수치와, 정답을 아는 검증 사례 | "돌아는 가는데 틀린 답을 내는" 결과를 한 번에 걸러낸다 |
| 하지 말 것 | git 상태 변경, 서버 실행, 다른 저장소 수정, 승인 대기 | 9번 절의 사고에서 나온 항목들이다 |
| 보고 형식 | 근거는 `파일:줄`, 확인한 것과 추정을 구분, 문제없던 항목도 "이상 없음"으로 기재 | 무엇을 실제로 봤는지 증명되어야 채택할 수 있다 |

## 5. 배정 방식 다섯 가지

| 방식 | 언제 쓰나 | 실제 사용 |
| --- | --- | --- |
| 단독 배정 | 범위가 한 워커에 들어가는 수정 | 대부분의 건 |
| 병렬 분담 | 서로 다른 파일을 고치는 일이 여러 개일 때 | 같은 시각에 코드 수정(`codex`)과 그 수정을 판정할 도구(`agy`)를 따로 발행 |
| 교차검증 | 원인이 불확실한 진단, 판정이 갈릴 수 있는 일 | 같은 브리프를 `codex`·`agy` 에 독립 발행하고 서로의 결과를 보지 못하게 함. 5회 |
| 분할 검수 | 문서·산출물 전체를 코드와 대조할 때 | 겹치지 않는 파일 범위를 나눠 읽기 전용으로 맡기고 지휘자가 지적을 전부 재확인. 1회 |
| 반복 감시 | 여러 워커가 동시에 고치는 동안 회귀를 지켜볼 때 | 한 워커가 주기마다 테스트·게이트·범위 이탈을 점검해 `watch/status.md` 에 기록 |

교차검증에서 결과가 갈리면 이렇게 처리한다. 양쪽이 같으면 채택하고, 한쪽만 찾았으면 지휘자가
코드로 확인한 뒤 채택하며, 결론이 상반되면 어느 쪽도 채택하지 않고 지휘자가 판정한다.
GPU 나 같은 파일을 동시에 건드리는 작업에는 교차검증을 쓰지 않는다.

- 소요 시간은 브리프 발행 시각부터 그 파일이 마지막으로 수정된 시각까지다. 결과를 나중에 고쳐 쓴
  경우 실제보다 길게 잡히므로 대략의 값으로 본다.
- 브리프 파일에 `## 결과` 가 없는 건이 9건(5%)이다. 보고 형식은 항상 지켜지지 않았고, 그래서 검수는
  보고서가 아니라 `git diff` 와 테스트를 기준으로 했다.
- 직접 쓴 브리프 14건 중 12건에 결과가 적혀 있다.

### 보드와 대조

- 보드에는 175행이 있고 그중 2건은 취소다(첫 배정 두 건, 사유는 범위 밖).
- 보드에 없는 브리프가 15건이다. 09-29 이후 직접 쓴 14건과 그 전의 1건이다.
- 제목에 "교차"가 붙은 배정은 11건, "재발행"이 붙은 배정은 6건이다. 재발행 가운데 1건은 워커가
  모델 서버에 닿지 못해 "서버 불필요" 조건으로 바꿔 다시 보낸 것이다.

## 8. 대표 사례

### 교차검증으로 원인 좁히기 (09-10)

- **증상**: 상품 종류가 달라도 상세페이지 6건 중 5건이 같은 10블록 순서였다. 코드가 블록을 채워
  넣던 동작을 없앤 뒤에도 5건이 같은 9블록이었다.
- **배정**: `codex` 와 `agy` 에 같은 브리프를 동시에 발행하고, 서로의 결과 파일을 열지 말라고 적었다.
- **결과**: 두 워커가 독립적으로 같은 결론을 냈다. "고정하지 말라"는 문장이 있어도 프롬프트 뒤쪽의
  순차 지시 목록이 순서를 사실상 정해 준다는 것이다. 제안서는 `.orchestration/proposals/` 에 남겼다.
- **이어진 일**: 프롬프트 개정 → 블록 구성이 여전히 고정이라 2차 교차검증 → 같은 날 "구성을 코드가
  정한다"는 설계로 전환했다.

### 분할 검수 (09-16)

- **배정**: 계약·아키텍처 문서, 운영·배포 문서, 산출물·차수 기록을 워커 세 명에게 겹치지 않게
  나눠 주고 파일 수정은 금지했다. 근거 없는 지적은 채택하지 않는다고 적었다.
- **결과**: 워커 보고 4건에서 지적 31건이 나왔다. 지휘자가 전부 코드와 문서에서 다시 확인해
  치명 4, 불일치 6, 사소 6, 기록만 4로 확정하고 5건은 기각했다.
- **이어진 일**: 다음 날 같은 세 워커에게 수정 → 재수정 → 정리 → 호칭 → 이름 변경 순으로
  라운드를 나눠 발행했다. 결과는 [`deliverables-review-2026-09-16.md`](../common/deliverables-review-2026-09-16.md)에 있다.

### 안전성 검증 세 갈래 병렬 (09-21)

- **배정**: 편향(`agy`), Prompt Injection(`codex`), 환각(`agy2`)을 같은 시각에 따로 발행했다.
- **결과**: 측정 결과가 [`ai-safety-report-2026-09-21.md`](../phase4/evaluation/ai-safety-report-2026-09-21.md)로
  정리됐고, 여기서 나온 문제로 수정 브리프 2건(프롬프트 구조 위조 방지, 상품 사진 확인 단계)과
  추가 실측 1건(사진 속 글자를 통한 주입)을 이어서 발행했다.

### 반복 감시 (09-09)

- **배정**: 여러 워커가 동시에 고치는 동안 `agy2` 에게 주기마다 전체 테스트, 컷아웃 게이트,
  허용 범위 밖 파일 변경, 완료된 브리프를 점검하게 했다.
- **결과**: 두 번째 사이클에서 허용 범위 밖 파일이 바뀐 것을 경고로 잡아냈다.

### 실제 사이트 전체 흐름 테스트 (10-01)

- **배정**: 사내 Ubuntu 서버에 FE·BE 사본을 띄우고 브라우저로 판매자 등록부터 상세페이지 게시까지
  돌리게 했다. 실제 FE·BE 저장소와 Stage 리소스는 건드리지 못하게 했다.
- **결과**: 화면·로그·JSON 증거 149개 파일이 `.orchestration/reports/` 에 쌓였고, BE 콜백을
  다시 보낼 때 필드 이름이 바뀌어 BE 가 500 을 내는 버그를 찾았다.

### 수정을 PR·머지까지 위임 (10-05)

- **배정**: 위 버그 수정을 PR 과 머지까지 맡겼다. 이 작업에 한해 git 사용을 허용하고, 커밋할 파일
  2개와 건드리면 안 되는 파일을 이름으로 적었다. `git add` 는 경로를 지정해서만 하게 했다.
- **결과**: 워커가 검토 단계에서 옛 형식 행 복원 테스트를 추가하고 오류를 삼키던 예외 처리를 없앴다.
  테스트 536개 통과 후 작업 저장소 PR, 조직 저장소 동기화 PR, 이미지 발행 확인까지 끝냈다.

### 워커의 검수 결과도 검증한다 (10-05)

- **배정**: 새로 쓴 저장소 README 를 워커에게 검수시켰다.
- **결과**: 지적 대부분은 코드·CI 와 대조해 반영했지만, 2건은 실제 배포 상태를 확인한 뒤 기각했다.
  워커의 지적도 근거를 다시 확인하기 전에는 사실로 취급하지 않는다.

### 다른 팀에 줄 수정안 작성 (10-01)

- **배정**: 챗봇 LLM 컨테이너가 메모리 초과로 죽는 문제에 대해 로그와 매니페스트를 읽기 전용으로
  주고, 원인 확인과 수정안만 쓰게 했다. 코드·설정 변경과 클러스터 명령은 금지했다.
- **결과**: 원인(프롬프트 캐시와 컨텍스트 체크포인트가 컨테이너 메모리를 키움)과 수정안이 나왔다.
  다른 팀 소관의 코드는 고치지 않았고, 이후 챗봇 쪽에서 프롬프트 캐시 상한 설정과 모델 사전 적재가 반영됐다.

| 워커 터미널을 찾지 못함 | CLI 가 터미널 제목을 자기 실행 명령으로 바꿨다 | 제목 대신 tty 로 워커를 찾는다 |

| 인계받은 세션이 작업 성격을 바꿈 | 점검 작업을 넘겨받아 수정으로 진행했다 | 인계 시 원래 작업의 목적과 금지 사항을 그대로 승계한다 |

## 10. 지금 쓰는 방식

2026-09-29 부터는 방식이 단순해졌다.

- **워커는 옆 터미널 한 명**이다(10-01 이후 Codex. 09-29 브리프는 파일 이름에 `neighbor` 를 붙였다).
  하루 배정이 1~6건으로 줄고 한 건의 범위가 커졌다.
- **브리프는 직접 쓴다.** 이름은 `<날짜>-<주제>.md` 이고, 배경·자료 위치·할 일·하지 말 것·보고 형식을
  적는다. 보드는 쓰지 않는다.
- **전달은 한 줄**이다. 워커 터미널에 "이 파일을 읽고 수행하라"만 보낸다.
- **기본 금지 사항**을 브리프마다 적는다. git 상태 변경, 실제 FE·BE 저장소 수정, Stage 리소스 조작,
  인프라 저장소 푸시가 여기에 든다.
- **증거는 `reports/<날짜>-<주제>/`** 에 모은다.
- **검수는 그대로**다. 워커의 결과와 지적은 지휘자가 코드·테스트·실제 상태로 확인한 뒤 채택한다.
